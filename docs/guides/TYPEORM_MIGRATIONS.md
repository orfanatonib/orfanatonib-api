# TypeORM migrations

## Status

The API has a shared TypeORM configuration for the NestJS application and the
TypeORM CLI. The entity registry lives in `database/database.entities.ts`, so a
new entity must be registered only once.

The initial schema baseline was generated by `migration:generate`; `up/down/up`
was validated on an empty disposable database. On `orfanato-nib-local`, a
read-only TypeORM schema diff confirmed the legacy schema matched the baseline;
the baseline was recorded as applied and the two Estúdio migrations were run.
Adoption and rollback rehearsal on restored staging/production environments
remain mandatory before rollout there. Existing environments were historically
created with `synchronize: true`; never run the baseline normally over those
tables.

## Production transition (rehearsed 2026-11-23)

Production (35 tables, no `typeorm_migrations`) is adopted by `scripts/deploy/database.cjs auto`:

1. schema fingerprint must equal `database/adoption/legacy-schema.json` (otherwise it aborts, nothing altered);
2. DB default collation is aligned to the tables' (`utf8mb4_0900_ai_ci`) so new FKs are compatible;
3. `LegacyProductionUpgrade1795459199000` brings the schema to the entities (18 new tables, 6 altered; `feature_flags.environment` is dropped exactly once);
4. `ReleaseBaseline1795459200000` is only *recorded* (fake), then `ReleaseDataPolicies1795459201000` runs;
5. `createSchemaBuilder().log()` must return 0 operations.

Later environments (already adopted) just run pending migrations. Empty databases run the baseline normally.
Entity ↔ migration map: `ENTITY_MIGRATION_MAP.md`. TypeORM `synchronize` is hard-coded `false` (no override).
Rehearsal rule: every rehearsal restores the **latest** S3 backup into a new database; never reuse a dump.

## Local commands

Run commands from `orfanatonib-api`:

```bash
npm run db:local:migration:generate -- database/migrations/DescriptiveName
npm run db:local:migration:status
npm run db:local:migration:deploy
npm run db:local:migration:revert
```

These commands load `env/local.env`. They must never be pointed at staging or
production. A migration file must only be created by `migration:generate` and
must not be edited manually.

## Schema-change workflow

1. Restore or create a disposable local database whose migrations are current.
2. Change the entity metadata and register a new entity in
   `database/database.entities.ts` when applicable.
3. Generate the migration through the local command.
4. Review the generated SQL without editing the migration.
5. Apply the migration to the disposable database.
6. Run `migration:status` and a drift check:

   ```bash
   npm run db:local:migration:generate -- database/migrations/DriftCheck --check
   ```

7. Revert and apply again to validate rollback and redeploy.
8. Run build and relevant tests.

## Baseline rollout for an existing environment

The baseline creates the complete schema and therefore must not execute normally
on a database that already contains those tables.

For each environment, the responsible operator must:

1. create and verify a recoverable database snapshot;
2. restore that snapshot to an isolated database;
3. compare the restored schema with the entity metadata and resolve all drift;
4. mark the baseline as applied on the isolated restored database using the
   TypeORM `migration:run --fake` option;
5. verify migration status and run the application test suite against the copy;
6. rehearse restore/rollback;
7. schedule the real rollout and only then set application synchronization to
   `false`.

The production rollout requires explicit authorization. Never fake a migration
before proving that the target schema already matches the baseline.

## Deployment order after baseline adoption

1. Take the required snapshot/backup.
2. Deploy code that remains compatible with both the old and new schema when a
   staged change is necessary.
3. Run pending migrations once through the deployment job.
4. Verify migration status and application health.
5. Deploy or enable code that depends on the new schema.

The deployment operator owns migration execution and evidence collection. The
application process must not run migrations automatically at startup.
